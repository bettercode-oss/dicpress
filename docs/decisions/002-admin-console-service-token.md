# ADR 002: 관리자 콘솔 연동을 고정 서비스 토큰으로 한다

## 상태

채택 (2026-08-23)

## 배경

dicpress 관리 기능을 `admin.bizos.kr` 통합 관리자 콘솔에서도 쓰려고 한다.
자체 관리자 UI(`dic.bizos.kr/admin`)는 당분간 그대로 둔다 — 두 화면을 나란히 띄워
같은 데이터를 보는 기간을 거쳐야 이식이 맞는지 알 수 있다.

Epic #68 과 이슈 #63 은 이 연동을 **60초짜리 actor JWT** 로 설계해 두었다.
그런데 그 설계는 콘솔이 아직 없는 앱이라는 전제 위에 있었고, 실제로 도는 콘솔은 다르다.

- 저장소는 `bettercode-oss/admin-console` 이 아니라 `ahnyounghoe/admin` 이고, 2026-08-22 에
  이미 배포되어 돌고 있다(포트 3004).
- 콘솔은 **자체 DB(`admin_bizos`)와 자체 사용자·자체 Passkey** 를 가진다.
  "dicpress User = 콘솔 User" 라는 전제가 성립하지 않는다.
- 콘솔은 이미 kbo-name-game 을 **고정 서비스 토큰**으로 연동해 두었다
  (`connectors/{product}.ts`, `import "server-only"`, `Authorization: Bearer`).

## 결정

**고정 서비스 토큰 + 행위자 이메일 헤더**로 연동한다. actor JWT 는 채택하지 않는다.

```
Authorization: Bearer <ADMIN_SERVICE_TOKEN>
X-Actor-Email:  <콘솔에 로그인한 사람의 이메일>
```

`lib/authz.ts` 의 `requireActor(req, roles?)` 가 두 경로를 모두 받는다.
서비스 토큰 경로든 세션 경로든 **매 요청 DB 에서 `role` 과 `status` 를 다시 읽어**
같은 모양의 `Actor` 로 수렴시킨다. 권한 정책은 `lib/document-access.ts` 한 곳에 그대로 남는다.

라우트를 새로 파지 않는다. 콘솔은 자체 UI 가 쓰는 경로를 그대로 호출한다.

**WebAuthn RP ID 는 `bizos.kr` 로 넓히지 않는다.** 이슈 #65 는 수행하지 않는다.

## 근거

**콘솔의 기존 관행과 같아야 한다.**
kbo-name-game 이 이미 고정 토큰으로 붙어 있다. dicpress 만 JWT 를 요구하면 콘솔에
`jose` 와 발급 로직이 새로 들어가고, 커넥터 두 개가 서로 다른 방식이 된다.
JWT 의 60초 만료가 사는 값은 "토큰이 새어도 60초 뒤 죽는다" 인데, 이 구조에서 토큰은
루프백 안에서만 오가므로 그 위험 자체가 작다.

**행위자를 함께 보내야 한다.**
두 앱의 사용자 DB 가 다르므로 토큰만으로는 누가 하는 일인지 알 수 없다. 문서의
`authorId`, AUTHOR 범위 정책, "자기 자신은 정지할 수 없다" 가 전부 행위자를 필요로 한다.
전용 서비스 계정 하나로 처리하면 콘솔에서 만든 문서의 작성자가 전부 그 계정이 되어
작성자 귀속이 사라진다.

**신뢰 경계는 nginx 에 둔다.**
토큰을 쥔 쪽은 `X-Actor-Email` 로 누구든 사칭할 수 있다. DB 에서 role 을 다시 읽는 것은
권한 상승은 막지만 사칭은 막지 못한다. 그래서 실질적인 방어를 앱 밖에 둔다 —
nginx 의 `location /` 에서 클라이언트발 `Authorization` 을 비운다.

이게 가능한 이유는 **dicpress 가 브라우저에서 `Authorization` 헤더를 한 번도 쓰지 않기**
때문이다(관리자 UI 는 전부 세션 쿠키). 헤더를 비우면 토큰 경로는 공개 인터넷에서 물리적으로
도달 불가능해지고, 루프백(`127.0.0.1:3001`)으로 들어오는 콘솔에서만 살아 있다.
처음에는 앱 안에서도 "`X-Forwarded-For` 가 있으면 외부 경유이므로 거절" 하는 보조 가드를
두었으나 **철회했다.** 실측해 보니 Next 는 클라이언트가 보낸 `X-Forwarded-For` 를 그대로
전달한다. 공격자가 `::1` 로 위조하면 그만이라 막아 주는 것이 없고, 개발 서버는 이 헤더를
항상 붙여서 로컬 개발만 깨진다. 안전하다는 착각만 주는 가드는 없느니만 못하다.
**경계는 전적으로 nginx 설정 한 줄에 있다.**

**그리고 그 한 줄은 저장소 밖에 있다.** CI 는 nginx 를 배포하지 않는다. 저장소의
`deploy/nginx.conf.template` 은 `setup.sh` 가 최초 1회만 읽는 원본일 뿐, 운영 설정의
사본이 아니다. 즉 이 구조에서 **가장 중요한 방어가 버전 관리도 배포도 되지 않는다.**

가정이 아니라 실제로 일어났다. #72 착수 시점에 서버의 dic vhost 에는 그 줄이 **아예 없었고**,
공개 URL 로 보낸 `Authorization` 이 앱까지 도달하고 있었다(더미 Bearer 에 503 응답으로 확인).
토큰이 아직 배포되기 전이라 실질 노출은 없었지만, 순서가 반대였다면 관리 API 가 인터넷에
열린 채였을 것이다.

그래서 **배포마다 감시한다.** `scripts/verify-auth-boundary.sh` 가 배포 워크플로 마지막에
돌면서 유효한 토큰을 공개 URL 로 보내 **401 이 나오는지** 확인한다. 401 이 아니면
헤더가 통과했다는 뜻이므로(200·403·400 모두) 워크플로를 실패시킨다. 롤백하지는 않는다 —
배포된 코드는 정상이고 문제는 nginx 설정이라 되돌린다고 고쳐지지 않는다.

이 감시에는 한 가지 사각이 있다. 리포지토리 시크릿의 토큰이 서버 값과 다르면, 헤더가
통과하더라도 토큰 불일치로 401 이 나와 **거짓 정상**이 된다. 스크립트가 값의 존재와 최소
길이는 확인하지만 "서버와 같은 값인가" 는 밖에서 알 수 없다. 토큰 회전 절차를 CLAUDE.md 에
표로 남긴 이유가 이것이다.

**RP ID 를 넓히지 않는 이유.**
콘솔은 `admin.bizos.kr` RP ID 로 이미 자체 Passkey 로그인이 동작한다. dicpress 의 RP ID 를
`bizos.kr` 로 낮출 이유가 없다. 오히려 낮추면 콘솔·kbo-name-game·dicpress 가 자격증명을
공유하게 되어 "서비스 토큰 API 로만 통신한다" 는 콘솔의 원칙이 인증 경계에서 깨진다.
게다가 RP ID 전환은 기존 Passkey 를 전부 무효화하는 **전원 잠금 위험**을 동반한다.
얻는 것 없이 그 위험을 치를 이유가 없다.

**라우트를 새로 파지 않는 이유.**
#63 은 `/api/admin/documents/*` 를 새로 만들고 기존 경로를 얇은 래퍼로 남기려 했다.
그것은 Phase 5 에서 `/api/documents/*` 를 **삭제**하는 것을 전제한 설계였다.
자체 UI 를 당분간 유지하는 이상 경로를 둘로 늘리면 표면만 넓어지고 인증을 틀릴 곳이
두 배가 된다. 두 UI 가 **같은 핸들러**를 지나는 것이 병행 운영에서 가장 중요한 성질이다.

**문서 쓰기가 dicpress 안에서 일어나야 하는 이유.**
`revalidatePath` 는 호출한 프로세스의 캐시만 무효화한다. 콘솔이 Prisma 로 직접 쓰면
공개 목록(`revalidate=60`), 상세(`600`), 사이트맵(`3600`)이 그만큼 낡은 채로 남는다.
BFF 로 dicpress API 를 지나면 캐시 무효화가 그대로 따라온다.

이 근거는 배포 후 운영에서 실측해 확인했다(#74). 다만 처음에는 **목록만 관통하지 않았다** —
`revalidatePath("/")` 는 기본 타입이 `'page'` 인데 키워드 목록은 `app/(public)/layout.tsx`
에서 조회하기 때문이다. `revalidatePath("/", "layout")` 으로 고쳤다.
"쓰기가 dicpress 안에서 일어나면 즉시 갱신된다" 는 명제는 **무효화 범위를 정확히 지정했을
때만** 참이다.

## 트레이드오프

### 사칭을 막지 못한다 — actor JWT 를 버린 대가

이것이 이 결정의 가장 큰 대가다. **토큰을 쥔 쪽은 `X-Actor-Email` 에 아무 주소나 실어
임의의 dicpress 사용자로 행동할 수 있다.** OWNER 이메일을 넣으면 OWNER 다.
DB 에서 role 을 다시 읽는 것은 권한 상승은 막지만 사칭은 막지 못한다.

actor JWT 였다면 콘솔이 자기 키로 "이 사람이 맞다" 를 서명해 주고 dicpress 가 그 서명을
검증했을 것이다. 고정 토큰에는 그 서명이 없다. 즉 **"누가 행위자인가" 에 대한 판단을
dicpress 가 콘솔에 통째로 위임한다.** 책임 경계는 이렇게 갈린다.

| 누가 | 무엇을 보장하는가 |
|---|---|
| nginx | 토큰 경로가 공개 인터넷에서 도달 불가능하다 |
| dicpress | 토큰이 맞는지, 그 계정이 실재하고 `ACTIVE` 인지, 그 `role` 로 무엇을 할 수 있는지 |
| **콘솔** | **어떤 콘솔 사용자가 어떤 이메일을 주장할 수 있는지** |

따라서 콘솔은 `X-Actor-Email` 을 반드시 서버 사이드 세션에서 채워야 하고, 브라우저가 그
헤더를 지정할 수 있는 경로(무제한 BFF passthrough 등)를 열어서는 안 된다.
이 책임은 `docs/admin-api.md` 에 계약으로 명시했다.

**특히 이 값을 고정해 두면 설계 전제가 통째로 무너진다.** 커넥터가 모든 요청에 같은 주소를
싣는 순간 "어떤 콘솔 사용자가 어떤 이메일을 주장할 수 있는가" 를 판단하는 지점이 **사라진다.**
그러면 콘솔에 로그인한 사람은 누구나 그 이메일의 권한(대개 OWNER)으로 dicpress 를 움직이게
되고, 문서 작성자도 전원 같은 계정으로 기록된다. dicpress 쪽에서는 정상적인 요청과 구분할
방법이 없다 — 토큰이 맞고 계정이 ACTIVE 이기 때문이다.

그래서 콘솔 커넥터는 행위자 이메일을 **인자로 받지 않는다.** 호출자가 값을 지정할 자리를
아예 만들지 않는 것이 유일하게 확실한 방어라는 판단이다. 인자를 열어두면 언젠가 폼이나
쿼리에서 온 값이 흘러들어간다.

값의 출처는 두 가지고 **우선순위가 있다.** `DICPRESS_ACTOR_EMAIL` 환경변수가 있으면 그 값이,
없으면 로그인 세션의 이메일이 쓰인다. 즉 "세션에서만 읽는다" 는 그 변수가 없을 때에 한해
참이다.

그 변수는 **로컬 전용 탈출구다.** 로컬 admin DB 의 Owner 이메일이 운영과 달라 그냥 부르면
403 이기 때문에 둔 것이다. 값이 있으면 세션과 무관하게 그 이메일로 행동하므로,
**운영 `.env` 에 나타나는 순간 위 방어가 꺼진 상태**가 된다. 인자를 막아 둔 것과 달리
이쪽은 설정 하나로 열리므로, 방어의 실효는 "그 변수가 운영에 없다" 에 걸려 있다.

즉 "그런 변수가 없다" 가 아니라 **"로컬에만 있어야 한다"** 가 정확한 서술이다. 그리고 이건
파일만 보면 알 수 있으므로 **점검 가능한 항목**이다 — nginx 의 `Authorization` 스트립을
배포마다 확인하는 것과 같은 종류의 감시가 콘솔 쪽에도 필요하다.

운영에 넣고 싶어지는 순간(콘솔 사용자가 늘었는데 dicpress 계정이 없을 때)이 오면, 할 일은
이 변수를 켜는 것이 아니라 **dicpress 에 그 사람 계정을 만드는 것**이다. 콘솔 안에 "이 콘솔
사용자는 저 dicpress 이메일" 보정표를 두는 것도 같은 이유로 안 된다 — 그 순간 판단 지점이
설정 파일로 새어 나간다. 계정이 없으면 403 이 나는 것이 정직한 실패다.

이 대가를 받아들인 이유는 위 「근거」에 적었다 — 콘솔의 기존 연동 방식과 같아야 하고,
JWT 의 60초 만료가 사는 값은 토큰이 루프백 안에서만 오가는 이 구조에서 크지 않다.
**콘솔이 여러 조직으로 열리거나 dicpress 외 서비스가 늘어 위임 범위가 넓어지면 재검토한다.**

### 그 밖에

- **nginx 한 줄이 사라지면 조용히 뚫린다.** CI 가 nginx 를 반영하지 않으므로 서버에서
  직접 관리해야 한다. 배포 후 `scripts/verify-auth-boundary.sh` 로 감시한다(#72).
- **인증되는 모든 요청에 DB 왕복이 1회 늘어난다.** `select` 를 좁혀 부담을 줄였다.
  대가로 강등·정지가 즉시 반영된다 — 지금까지는 JWT 에 박힌 role 때문에 세션 만료까지
  예전 권한이 살아 있었다.
- **콘솔 사용자와 dicpress 사용자를 같은 이메일로 맞춰 두어야 한다.** 없으면 403 이고,
  dicpress 는 계정을 자동으로 만들지 않는다. 주소는 소문자로 정규화해 비교한다.
- **퇴사자 이메일을 재사용하면 권한이 자동 승계된다.** 행위자를 이메일로 식별하는 구조의
  직접적인 귀결이다. 계정 정리는 `SUSPENDED` 또는 삭제로 하고, 주소는 재사용하지 않는다.
- **토큰 회전에 무중단 절차가 없다.** 필요해지면 콤마 구분 다중값을 받도록 넓힌다.
- **문서를 한 건 고칠 때마다 공개 캐시가 통째로 날아간다.** 목록을 갱신하려면 `'layout'`
  무효화가 필요한데 그 범위가 하위 페이지 전부이기 때문이다(#74). 편집기가 10초마다
  자동저장하므로 편집 중에는 공개 페이지가 거의 캐시되지 않는다. 문서 수가 적어 재생성
  비용이 낮은 동안 감수한다. 조건을 좁히는 대신 단순함을 택한 이유는, 바로 그런 영리한
  조건이 직전에 우리를 물었기 때문이다(#72).
- **토큰이 없거나 32자 미만이면 서비스 토큰 경로 자체를 비활성화한다**(기동 시 1회 경고).
  이때도 세션 경로는 살려 둔다 — 콘솔 연동이 안 되는 것보다 자체 관리자 UI 가 죽는 쪽이
  훨씬 큰 사고다.

## 병행 운영의 종료 조건

콘솔 화면이 자체 UI 와 같은 것을 보여준다는 것을 **기간을 두고 대조 확인**한 뒤에
dicpress 의 `/admin` 을 닫는다(#67). 그 시점에 `lib/authz.ts` 의 세션 경로를 걷어내고
nginx 에서 관리 API 를 경로째 막는다. 지금 막으면 자체 UI 가 죽는다.
