# ADR 002: 관리자 콘솔 연동을 고정 서비스 토큰으로 한다

## 상태

채택 (2026-08-23)

## 배경

dicpress 관리 기능을 `admin.bizos.kr` 통합 관리자 콘솔에서도 쓰려고 한다.
자체 관리자 UI(`dic.bizos.kr/admin`)는 당분간 그대로 둔다 — 두 화면을 나란히 띄워
같은 데이터를 보는 기간을 거쳐야 이식이 맞는지 알 수 있다.

Epic #68 과 이슈 #63 은 이 연동을 **60초짜리 actor JWT** 로 설계해 두었다.
그런데 그 설계는 콘솔이 아직 없는 앱이라는 전제 위에 있었고, 실제로 도는 콘솔은 다르다.

- 저장소는 `bettercode-oss/admin-console` 이 아니라 `ahnyounghoe/admin` 이고, 2026-08-22 에
  이미 배포되어 돌고 있다(포트 3004).
- 콘솔은 **자체 DB(`admin_bizos`)와 자체 사용자·자체 Passkey** 를 가진다.
  "dicpress User = 콘솔 User" 라는 전제가 성립하지 않는다.
- 콘솔은 이미 kbo-name-game 을 **고정 서비스 토큰**으로 연동해 두었다
  (`connectors/{product}.ts`, `import "server-only"`, `Authorization: Bearer`).

## 결정

**고정 서비스 토큰 + 행위자 이메일 헤더**로 연동한다. actor JWT 는 채택하지 않는다.

```
Authorization: Bearer <ADMIN_SERVICE_TOKEN>
X-Actor-Email:  <콘솔에 로그인한 사람의 이메일>
```

`lib/authz.ts` 의 `requireActor(req, roles?)` 가 두 경로를 모두 받는다.
서비스 토큰 경로든 세션 경로든 **매 요청 DB 에서 `role` 과 `status` 를 다시 읽어**
같은 모양의 `Actor` 로 수렴시킨다. 권한 정책은 `lib/document-access.ts` 한 곳에 그대로 남는다.

라우트를 새로 파지 않는다. 콘솔은 자체 UI 가 쓰는 경로를 그대로 호출한다.

**WebAuthn RP ID 는 `bizos.kr` 로 넓히지 않는다.** 이슈 #65 는 수행하지 않는다.

## 근거

**콘솔의 기존 관행과 같아야 한다.**
kbo-name-game 이 이미 고정 토큰으로 붙어 있다. dicpress 만 JWT 를 요구하면 콘솔에
`jose` 와 발급 로직이 새로 들어가고, 커넥터 두 개가 서로 다른 방식이 된다.
JWT 의 60초 만료가 사는 값은 "토큰이 새어도 60초 뒤 죽는다" 인데, 이 구조에서 토큰은
루프백 안에서만 오가므로 그 위험 자체가 작다.

**행위자를 함께 보내야 한다.**
두 앱의 사용자 DB 가 다르므로 토큰만으로는 누가 하는 일인지 알 수 없다. 문서의
`authorId`, AUTHOR 범위 정책, "자기 자신은 정지할 수 없다" 가 전부 행위자를 필요로 한다.
전용 서비스 계정 하나로 처리하면 콘솔에서 만든 문서의 작성자가 전부 그 계정이 되어
작성자 귀속이 사라진다.

**신뢰 경계는 nginx 에 둔다.**
토큰을 쥔 쪽은 `X-Actor-Email` 로 누구든 사칭할 수 있다. DB 에서 role 을 다시 읽는 것은
권한 상승은 막지만 사칭은 막지 못한다. 그래서 실질적인 방어를 앱 밖에 둔다 —
nginx 의 `location /` 에서 클라이언트발 `Authorization` 을 비운다.

이게 가능한 이유는 **dicpress 가 브라우저에서 `Authorization` 헤더를 한 번도 쓰지 않기**
때문이다(관리자 UI 는 전부 세션 쿠키). 헤더를 비우면 토큰 경로는 공개 인터넷에서 물리적으로
도달 불가능해지고, 루프백(`127.0.0.1:3001`)으로 들어오는 콘솔에서만 살아 있다.
처음에는 앱 안에서도 "`X-Forwarded-For` 가 있으면 외부 경유이므로 거절" 하는 보조 가드를
두었으나 **철회했다.** 실측해 보니 Next 는 클라이언트가 보낸 `X-Forwarded-For` 를 그대로
전달한다. 공격자가 `::1` 로 위조하면 그만이라 막아 주는 것이 없고, 개발 서버는 이 헤더를
항상 붙여서 로컬 개발만 깨진다. 안전하다는 착각만 주는 가드는 없느니만 못하다.
**경계는 전적으로 nginx 설정 한 줄에 있다.**

**RP ID 를 넓히지 않는 이유.**
콘솔은 `admin.bizos.kr` RP ID 로 이미 자체 Passkey 로그인이 동작한다. dicpress 의 RP ID 를
`bizos.kr` 로 낮출 이유가 없다. 오히려 낮추면 콘솔·kbo-name-game·dicpress 가 자격증명을
공유하게 되어 "서비스 토큰 API 로만 통신한다" 는 콘솔의 원칙이 인증 경계에서 깨진다.
게다가 RP ID 전환은 기존 Passkey 를 전부 무효화하는 **전원 잠금 위험**을 동반한다.
얻는 것 없이 그 위험을 치를 이유가 없다.

**라우트를 새로 파지 않는 이유.**
#63 은 `/api/admin/documents/*` 를 새로 만들고 기존 경로를 얇은 래퍼로 남기려 했다.
그것은 Phase 5 에서 `/api/documents/*` 를 **삭제**하는 것을 전제한 설계였다.
자체 UI 를 당분간 유지하는 이상 경로를 둘로 늘리면 표면만 넓어지고 인증을 틀릴 곳이
두 배가 된다. 두 UI 가 **같은 핸들러**를 지나는 것이 병행 운영에서 가장 중요한 성질이다.

**문서 쓰기가 dicpress 안에서 일어나야 하는 이유.**
`revalidatePath` 는 호출한 프로세스의 캐시만 무효화한다. 콘솔이 Prisma 로 직접 쓰면
공개 목록(`revalidate=60`), 상세(`600`), 사이트맵(`3600`)이 그만큼 낡은 채로 남는다.
BFF 로 dicpress API 를 지나면 캐시 무효화가 그대로 따라온다.

## 트레이드오프

- **토큰 하나가 OWNER 권한과 맞먹는다.** nginx 설정이 방어의 핵심이라, 그 한 줄을 지우면
  토큰이 인터넷에 노출된다. nginx 는 CI 가 반영하지 않으므로 서버에서 직접 관리해야 한다.
  대신 감사 로그(`console.warn` + `maskEmail`)로 토큰 경로의 변경 작업을 남긴다.
- **인증되는 모든 요청에 DB 왕복이 1회 늘어난다.** `select` 를 좁혀 부담을 줄였다.
  대가로 강등·정지가 즉시 반영된다 — 지금까지는 JWT 에 박힌 role 때문에 세션 만료까지
  예전 권한이 살아 있었다.
- **콘솔 사용자와 dicpress 사용자를 같은 이메일로 맞춰 두어야 한다.** 없으면 403 이고,
  dicpress 는 계정을 자동으로 만들지 않는다. 이메일 대소문자도 정확히 일치해야 한다.
- **토큰 회전에 무중단 절차가 없다.** 필요해지면 콤마 구분 다중값을 받도록 넓힌다.

## 병행 운영의 종료 조건

콘솔 화면이 자체 UI 와 같은 것을 보여준다는 것을 **기간을 두고 대조 확인**한 뒤에
dicpress 의 `/admin` 을 닫는다(#67). 그 시점에 `lib/authz.ts` 의 세션 경로를 걷어내고
nginx 에서 관리 API 를 경로째 막는다. 지금 막으면 자체 UI 가 죽는다.
